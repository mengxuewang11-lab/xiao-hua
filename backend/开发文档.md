```text

├── pom.xml
├── src/
│   ├── main/
│   │   ├── java/.../
│   │   │   ├── identity/
│   │   │   ├── novel/
│   │   │   ├── character/

│   │   │   ├── admin/
```

每个领域模块内部再按 `api`、`application`、`domain`、`infrastructure` 组织，避免整个项目横向堆放 Controller、Service、Repository。

## 2. API 分区

```text
/api/{控制器}/{接口名}           用户 Web 与 App
/admin-api/{控制器}/{接口名}     管理系统
/actuator/...                    运行监控，生产环境严格限制
```

业务接口路径必须使用 `com.xiaohua.novel.shared.api.ApiPaths` 中的统一常量，不要在 Controller、CORS 或 Security 配置里分散手写 `/api`、`/admin-api` 前缀。

示例：

```text
POST /api/novel-agent/runs
GET  /api/test/database
```

前端项目可以把请求客户端的 `baseURL` 设置为 `http://localhost:8080/api`，业务代码中只写 `/novel-agent/runs`；浏览器最终发出的真实请求仍然是 `/api/novel-agent/runs`。

响应统一包含业务错误码和 `requestId`。不要把异常堆栈返回客户端。

临时测试接口 `/api/test/**` 由 `TEST_ENDPOINTS_ENABLED` 控制。当前本地单机开发默认开启，生产环境必须显式关闭。

## 3. OpenAPI 与权限规范

### 3.1 文档入口

```text
Swagger UI：/swagger-ui.html
OpenAPI JSON：/v3/api-docs
```

Swagger 是接口文档入口，不属于业务控制器路径，因此不放在 `/api/{控制器}/{接口名}` 规则下。

本地使用 `SWAGGER_ENABLED=true`，不需要对外暴露接口文档的环境设置为 `false`。

Swagger 中的锁图标和 `Authorize` 只负责描述、保存并发送认证信息，真正的访问控制由 Spring Security 完成，不能把 Swagger 配置当作权限校验。

### 3.2 接口中文说明

每个 Controller 和接口必须补齐中文 OpenAPI 注解：

- Controller 使用 `@Tag` 说明模块用途。
- 接口使用 `@Operation`，`summary` 用一句中文说明用途，`description` 说明调用场景、限制和副作用。
- 使用 `@ApiResponse` 或 `@ApiResponses` 说明成功与常见错误状态。
- DTO 字段使用 `@Schema` 说明字段语义和示例。
- 受保护接口使用 `@SecurityRequirement(name = OpenApiConfig.BEARER_AUTH)`，确保 Swagger 显示锁图标。
- 公开接口不得错误标记为需要认证。

新增接口的验收标准包括：运行时权限正确、Swagger 中文描述完整、请求与响应模型可读。

### 3.3 Bearer Token

请求格式统一为：

```http
Authorization: Bearer <token>
```

当前本地单机开发默认关闭认证，便于快速联调。需要测试安全骨架时设置 `APP_AUTH_ENABLED=true`，并使用环境变量 `APP_AUTH_TOKEN` 配置静态开发令牌。Swagger 点击 `Authorize` 后只输入令牌本身，不输入 `Bearer ` 前缀。

正式认证阶段替换为：

```text
登录/刷新接口
→ 服务端签发短期 Access Token 和长期 Refresh Token
→ Spring Security 校验 JWT
→ 根据用户、角色和权限访问 /api 与 /admin-api
```

开发静态令牌不得用于生产；真实令牌不得写入仓库、日志或接口文档示例。管理接口还需增加角色权限和操作审计。

## 4. 数据库与 Flyway 规范

### 4.1 基本约定

- 使用 MySQL 8.0 和 `utf8mb4`。
- Flyway 是表结构、索引、约束和基准数据变更的唯一入口。
- 开发、测试、预发布和生产使用同一套迁移文件。
- `ddl-auto` 使用 `validate`，不得使用 `update`、`create` 或 `create-drop`。
- 所有时间统一保存明确时区语义。
- 软删除、乐观锁和状态枚举按业务需要设计。
- 长事务中不得等待模型返回。
- 模型生成结果先进入任务草稿，确认时再开启数据库事务。

### 4.2 迁移目录与命名

```text
src/main/resources/db/migration/
├── V1__initialize_schema.sql
├── V2__add_identity_tables.sql
├── V3__add_chapter_indexes.sql
└── R__database_views.sql
```

规则：

- 使用正向递增版本，版本号不得重复。
- 描述使用小写英文和下划线，名称需要说明实际变更。
- `V` 迁移只执行一次。
- `R` 迁移在校验值变化时重新执行，只用于视图等可重复对象。
- 一个迁移聚焦一个可说明、可评审的数据库变更。

### 4.3 不可变规则

- 已在任何共享环境执行的 `V` 迁移禁止修改、删除、重命名或调整顺序。
- 发现旧迁移有问题时，新增更高版本迁移修复。
- 不允许在 Workbench 中手工改表后不补迁移。
- 本地尚未共享且从未执行的草稿迁移可以在提交前整理。
- Flyway 会通过 `flyway_schema_history` 记录版本、校验值、执行时间和结果。

### 4.4 启动顺序

```text
Spring Boot 启动
→ Flyway 校验 flyway_schema_history
→ 执行尚未运行的迁移
→ Hibernate ddl-auto=validate
→ 应用开始对外提供服务
```

Flyway 失败或实体映射校验失败时，应用必须拒绝启动。

### 4.5 环境与发布

- 本地开发可以删除并重建本地数据库，但不能改写已提交迁移历史。
- 测试使用 Testcontainers MySQL 从空库执行全部迁移。
- 上线前在预发布环境验证从当前生产版本升级到目标版本。
- 生产迁移必须先备份并评估锁表、数据量和回滚方案。
- 大表变更需要拆成兼容的多阶段迁移，避免长时间锁表。
- 应用代码与数据库变更需要保持前后兼容，避免先迁移后应用或滚动发布期间失败。

### 4.6 禁止操作

- 生产环境禁止 `flyway clean`。
- 不把 `flyway repair` 放进自动启动或 CI/CD。
- `repair` 只能用于确认后的历史表修复，不能掩盖脚本被错误修改。
- 禁止让 Hibernate 代替 Flyway 创建或升级业务表。
- 禁止使用 MySQL `root` 作为应用连接账户。

### 4.7 Spring Boot 配置基线

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    clean-disabled: true
    validate-on-migrate: true
  jpa:
    hibernate:
      ddl-auto: validate
```

项目创建时还需加入 `flyway-core` 和 `flyway-mysql` 依赖。

## 5. AI 模块

```text
AIService
├── ContextBuilder
├── PromptBuilder
├── ResponseParser
└── ModelProvider
    ├── FakeModelProvider
    └── FutureVendorProvider
```

Provider 统一普通生成、流式生成、结构化生成、错误和用量。模型厂商确定前不创建 OpenAI 专属业务接口。

当前分为两条线：

- `agent.provider.NovelModelProvider`：服务 NovelAgent 自动写作状态机，当前仍使用 Fake Provider 验证长流程。
- `chat.application.ChatModelGateway`：服务 Web 对话工作台，已经接入真实 HTTP Chat Completions 风格接口，用于普通对话和需求讨论。

Web 对话工作台当前开放模型：

```text
zhipu / glm-4.7-flash         默认，智谱官方免费文本模型
zhipu / glm-4-flash-250414    智谱免费备用模型
kimi  / kimi-k2.6             Kimi 官方示例模型，是否免费取决于账号额度
```

真实模型密钥只从服务端环境变量读取：

```text
ZHIPU_API_KEY
KIMI_API_KEY
```

前端不得直接持有模型 API Key。

## 6. 事务边界

章节确认事务至少包含：

- 章节正文与摘要。
- 人物状态变化。
- 事件与时间线。
- 伏笔状态变化。
- StoryBible 正式事实。
- 冲突处理结果。
- 当前章节进度。

任一步失败则全部回滚。

## 8. 测试

- 领域规则使用普通 JUnit 单元测试。
- Repository 与 Flyway 使用 Testcontainers MySQL。
- CI 中必须从空 MySQL 容器执行全部 Flyway 迁移。
- 至少测试一次旧版本数据库升级到当前版本。
- Controller 使用 MockMvc 或集成测试。
- 受保护接口至少测试缺少令牌、错误令牌、合法令牌和权限不足。
- OpenAPI 至少验证中文摘要、响应说明和 Bearer 安全声明。
- AI 使用 Fake Provider。
- 主链路测试覆盖事务回滚和幂等重试。

## 9. Web 对话工作台后端

当前新增 `chat` 模块，服务用户 Web 首页，不替代 NovelAgent 状态机。

接口：

```text
GET  /api/chat/models
GET  /api/chat/preferences
PUT  /api/chat/preferences
GET  /api/chat/conversations
POST /api/chat/conversations
GET  /api/chat/conversations/{conversationId}
POST /api/chat/messages
```

表：

```text
app_user_profile          本地用户占位，后续接正式登录
user_ui_preference        主题、自定义色、侧边栏折叠、默认模型
chat_conversation         聊天会话摘要
chat_message              用户和助手消息
chat_model_call_record    模型调用审计、用量、失败原因
```

设计原则：

- 当前使用固定 `local-user`，表结构保留 `user_id` 以便后续接 JWT 用户。
- 主题和侧边栏状态必须走后端持久化，不能只放浏览器内存。
- 发送消息时先保存用户消息，再调用模型；模型失败也保留会话和失败记录，方便排查。
- 外部模型调用不放入长数据库事务。
- Kimi 和智谱接口由后端统一调用，客户端只传 `provider` 与 `model`。

## 10. 开发顺序

1. 以根目录 `NovelAgent状态机与决策规则.md` 为状态、恢复和决策基线。
2. 评审 `数据库设计-第一阶段.md`，数据库必须表达运行、步骤、草稿、检查点和正式事实隔离。
3. 通过新增 Flyway 版本创建业务表，不修改已经执行的迁移。
4. 实现状态机领域规则、Repository 和 DecisionManager。
5. 使用 Fake Provider 跑通初始化、单章生成、检查和自动修订。
6. 跑通连续3章、暂停恢复、幂等和事务回滚验收。
7. 接入真实 Provider，并将稳定性目标扩展到连续10章。
8. 核心闭环稳定后再扩展用户 Web、管理系统和 App。
